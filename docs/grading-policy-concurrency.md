# 成绩权重的旧表单防护

`PUT /api/v1/classes/:classId/grading-policy` 现在必须携带 `expected_weights`：最近一次 GET（或成功 PUT 返回）的完整13项权重数值，含4项顶层权重和9项流程细节权重。实际更新字段仍可只提供部分。

服务端在同一事务的 `SELECT ... FOR UPDATE` 行锁内：

1. 检查班级权重是否存在。
2. 比较全部13项期望值与当前数值；任意不一致则回滚并返回409，绝不写入旧表单。
3. 将补丁与当前记录合并，校验顶层和流程细节总和各为100。
4. 写入、读取本次结果并提交，再返回数据。

即使旧表单的总和仍是100，也不能覆盖另一编辑者修改过但本次未编辑的维度。这里只比较权重内容，不是单调递增版本：修改后完全恢复相同数值的记录仍可匹配快照。

- 400：缺少/不完整的期望快照、没有任何更新字段或权重总和非法。
- 403/404：保留原权限和不存在语义。
- 409：快照过期；重新GET并重新确认编辑，不自动重放旧PUT。

前端保留独立加载基线；编辑、恢复默认都不能修改该基线。成功保存后从响应更新基线；409时保留旧表单展示、禁止再次保存，提供明确“重新加载”操作。班级切换或卸载后忽略旧保存响应，保存期间禁止编辑数值。

## 发布与兼容性

无数据库迁移。前后端需要配套发布；旧客户端不携带快照会被400拒绝，不能继续静默覆盖。升级后要求旧页面刷新。OpenAPI及生成类型同步更新，不能为兼容旧写入而省略快照检查。

## 回归

- 服务测试：合法补丁、合法总和但陈旧的完整表单、未编辑流程细节冲突、锁内总和、回滚/提交错误。
- 控制器/Schema：快照必填、完整性、409映射。
- 前端：默认值不污染基线、成功保存刷新基线、冲突后重新加载、跨班级旧响应隔离。
- 真实UI：两个旧标签页操作隔离班级8404；首个保存35/20/20/25后，旧页40/15/25/20被409拒绝；重新加载后可保存。测试后通过UI恢复该班级40/20/20/20，未改8401或8402及既有报告成绩。
